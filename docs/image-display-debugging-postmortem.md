# Keyboard Vault 首页图片不可见问题复盘

## 背景

Keyboard Vault 是一个基于 React、TypeScript 和 File System Access API 的本地优先收藏管理应用。收藏数据使用 Markdown 保存，图片保存在用户选择的本地 vault 中。

问题出现在 Chrome 中：收藏的封面图片在编辑界面可以正常预览，但回到首页卡片后只显示黑色区域。刷新、重新上传以及重新编辑图片都不能解决。

## 用户可见现象

- 编辑器能够正常显示刚选择的图片。
- 保存后首页封面区域保持黑色。
- 页面没有明显报错。
- 图片文件实际存在于 `assets/images/`。
- 新生成的缩略图也不能在首页显示。

这组现象表明，问题不一定发生在上传、文件写入或图片解码阶段，也可能发生在图片组件的布局阶段。

## 排查过程

### 1. 检查图片数据和引用

首先检查了 Markdown 中的 `images.hero` 字段、图片文件名以及本地目录结构。确认大部分 Markdown 引用都能找到对应的 JPEG 文件，图片格式和文件尺寸也正常。

同时发现内置示例数据存在图片地址被重复解析的问题：已经由 Vite 转换过的站内资源地址，又被当成本地裸文件名解析，失败后变成空字符串。这个问题会让示例首页直接进入占位图分支，因此先修复了资源地址的幂等解析。

### 2. 引入缩略图机制

为了降低收藏数量增长后的资源占用，为图片链路增加了向后兼容的缩略图字段：

```yaml
images:
  hero: example.jpg
  thumbnail: example-thumb.jpg
```

新上传图片会生成最长边 2048px 的主图和最长边 640px 的缩略图。首页优先读取缩略图，详情与编辑页面继续读取主图。旧 Markdown 没有缩略图时自动回退到主图。

### 3. 排除 Chrome 懒加载问题

首页卡片使用了 `loading="lazy"`，而连接本地目录后的图片以 Data URL 形式提供。考虑到 Chrome 在嵌套滚动容器中的懒加载行为，曾将其调整为立即加载并异步解码。

修改后问题仍然存在，说明懒加载只是表象差异，不是真正根因。

### 4. 从“已加载”转向验证“实际可见”

早期验证只检查了：

- `<img>` 是否存在；
- `naturalWidth` 是否大于 0；
- 浏览器是否产生加载错误。

这些指标均正常，但用户仍看不到图片。于是进一步读取封面元素的实际布局信息，包括 `position`、`width`、`height` 和父容器尺寸。

最终发现：图片已经成功解码，父卡片高度也正常，但 `CoverImage` 外层容器的计算高度为 `0px`。

## 根因

`CoverImage` 组件内部固定添加了 `relative`：

```tsx
<div className={`relative overflow-hidden ... ${className}`}>
```

卡片调用方同时传入了：

```tsx
className="absolute inset-0"
```

最终元素同时具有 `relative` 和 `absolute`。由于 Tailwind 工具类在样式表中的生成顺序不等于 JSX 中的类名顺序，浏览器最终采用了 `position: relative`。

该元素内部只有绝对定位的图片，没有普通文档流内容，因此自身高度塌缩为 0。结果是：

- 图片成功加载；
- 图片自然尺寸正常；
- 没有触发 `onError`；
- 编辑器可以显示同一图片；
- 首页只能看到卡片背后的黑色背景。

## 修复方案

去掉封面组件外层强制设置的 `relative`，让调用方决定外层定位方式；同时让图片和占位内容通过 `width: 100%`、`height: 100%` 填充容器，不再依赖内部绝对定位。

修复后的职责划分是：

- 卡片和详情页决定封面容器的位置与尺寸；
- `CoverImage` 只负责填满给定容器、处理图片错误和显示占位内容。

## 验证结果

- 修复前封面容器高度：`0px`。
- 修复后封面容器高度：约 `331px`，与卡片图片区一致。
- 图片自然尺寸与实际可见尺寸均正常。
- Chrome 首页图片恢复显示。
- 编辑器和详情页没有回归。
- 真实 vault 中 14 个有效主图引用全部能找到对应文件。
- 自动化测试、TypeScript 构建和静态检查通过。

新增了组件布局回归测试，确保卡片传入 `absolute inset-0` 时，`CoverImage` 不会再次强制加入冲突的 `relative`。

## 调试经验

1. 图片“加载成功”不等于图片“用户可见”。除了网络和解码状态，还要检查实际布局尺寸、层叠关系、透明度和裁剪区域。
2. Tailwind 冲突类的结果取决于生成 CSS 的顺序，不能依赖 JSX 中后出现的类覆盖前面的类。
3. 当编辑器正常、列表异常时，应优先比较两处组件树、布局方式和加载属性，而不是反复处理图片文件。
4. 修复验证应覆盖真实用户目录，而不能只依赖内置示例数据。
5. 调试过程中发现的性能问题可以顺势治理，但每次修改后仍要回到原始症状，重新验证根因是否真正消失。

## 项目价值

这次修复不仅解决了单个显示问题，还完善了图片链路：

- 修复站内图片地址的重复解析；
- 支持 HEIC 等图片统一转换；
- 新增主图与缩略图双版本存储；
- 保持旧 Markdown 向后兼容；
- 为真实本地目录增加引用完整性验证；
- 建立组件布局层面的回归测试。

最终将一次表面上的“图片加载失败”，定位为 CSS 定位冲突导致的零高度布局问题，并同时提升了图片系统的可靠性、性能和可维护性。
